# CI toolchain durable fix — S0/S1 (owner: devops-engineer)

**Date:** 2026-07-13 · **Branch:** `feature/s0-s1-foundation-auth` · **CI loop:** ~8

This is now a **build-toolchain/environment** problem (devops-owned), not an app
defect. It has burned ~7 CI iterations. Below is the durable fix, an explicit
answer to the "move to latest npm?" question, and a foolproof command sequence to
regenerate + prove a cross-platform-correct lockfile.

---

## Root cause (confirmed, single class)

The **npm cross-platform optional-dependencies lockfile bug (npm/cli#4828)**. The
lock is generated on the dev's **macOS (darwin-arm64)**; CI runs **linux-x64**. A
lock generated on darwin can omit the linux-x64 native optional deps CI needs, so
`npm ci` on the linux runner fails. Two native deps have bitten us:

- `@biomejs/cli-linux-x64` — biome 1.9.4's platform CLI binary (still in play).
- `@rolldown/binding-linux-x64-gnu` — only when **vite 8** was used (vite 8 pulls
  rolldown). The pinned **vite 5.4** avoids rolldown entirely.

**New finding this iteration (important):** the three `package.json` manifests were
**still the broken "experiment" state at HEAD** (vite `8.1.4`, vitest `^4.1.10`, a
stray root `dependencies` block, openapi-ts `0.99`), and the committed lock had
17 `@rolldown/binding` entries. The engineer's two "Restore clean…" commits
(`4e41896`, `358f93e`) **did not actually land the pinned values** — the manifests
had reverted again. Repeated silent reverts are themselves the durable problem, so
the fix below includes a **machine-checked guardrail** so this class can never
merge again regardless of who runs which npm command.

---

## Should we move to the latest stable npm? — NO. Pin one, don't chase "latest".

"Latest" **without pinning re-introduces the exact drift we are fighting** (the
lock gets generated by whatever npm the dev happens to have, then consumed by a
different npm in CI). The fix is to **pin ONE npm used identically in generation
and CI**, and to generate/validate the lock on **linux**.

**Chosen npm: `npm@12.0.1`** (latest npm 12, per CLAUDE.md stack target `npm ~12`), declared as
`"packageManager": "npm@12.0.1"` in the root `package.json` and installed
explicitly in every npm-consuming CI job.

Note: toolchain was upgraded from npm@12.0.1 → npm@12.0.1 and Node 26 → Node 26 on
2026-07-13 (ADR-0005). npm/cli#4828 remains unresolved in npm 12 — the lockfile-guard
CI job and regen-lockfile workflow are retained unchanged (mechanism only, version strings bumped).

---

## The durable fix — defense in depth (three layers)

1. **Pin the resolver, identically both places.**
   - Root `package.json`: `"packageManager": "npm@12.0.1"` (single source of truth;
     honored locally by corepack and by anyone reading the manifest).
   - `.github/workflows/ci.yml`: `npm i -g npm@12.0.1` after each `setup-node`
     (jobs `verify`, `migrations`, `integration`, `sca`). Generation and
     consumption now use the same npm.

2. **Generate/validate the lock on LINUX matching CI** (the most robust layer —
   removes the "works on my Mac" gap at the source). The human regenerates the lock
   inside `docker run node:26` (linux-x64), so the committed lock natively contains
   the linux optional deps. A modern npm records **all** platforms' optional deps in
   the lock, so the same lock still serves local macOS dev. See command sequence.

3. **A binding CI guardrail — `lockfile-guard`** (wired into `all-green`). It
   hard-fails, with a clear actionable message, if:
   - the committed lock is **missing `@biomejs/cli-linux-x64`** (darwin-only lock), or
   - the lock **contains `@rolldown/binding`** (vite 8 crept back in).
   This converts the old cryptic `npm ci` "missing X from lock" cascade into a fast,
   obvious failure, and makes the whole bug class **impossible to merge** even if a
   future dev regenerates the lock on a Mac.

**Pins preserved (unchanged, as required):** vite `5.4.21`, vitest `2.1.9`
(+ `@vitest/coverage-v8 2.1.9`), biome `1.9.4`. `verify.sh` **not touched**
(PM-owned control). No application logic changed.

**What I edited:** root/`apps/api`/`apps/web` `package.json` (restored to the
documented clean/pinned state + added `packageManager`), `.github/workflows/ci.yml`
(npm pin steps + `lockfile-guard` job). `openapi-ts.config.ts` (already 0.53.x API)
and `biome.json` (already scoped) were already correct — left as-is.

## FOOLPROOF human command sequence (regenerate + prove the lock, then commit)

`git commit` / `npm install` cannot run in the Claude sandbox — a human runs this.
Run from the repo root on branch `feature/s0-s1-foundation-auth`, **in order**. Do
**not** interleave any `git checkout .` / `git reset --hard` / `git stash pop` /
`git restore` — those are how the manifests kept reverting.

```bash
# 0) Sanity: correct branch, and only the intended files are modified.
git rev-parse --abbrev-ref HEAD        # -> feature/s0-s1-foundation-auth
git status --short                     # expect the 3 package.json + docs; NOT app source
git stash list                         # must be EMPTY

# 1) Regenerate the lock INSIDE LINUX (node:26), pinned to npm 10.9.3. This is the
#    fix: the lock is produced on linux-x64 with the pinned resolver, so it contains
#    @biomejs/cli-linux-x64 (and all other platforms' optional deps).
#    Requires Docker / Rancher Desktop running.
rm -f package-lock.json
docker run --rm -v "$PWD":/w -w /w node:26-bookworm-slim bash -euo pipefail -c '
  npm i -g npm@12.0.1
  npm --version                         # -> 10.9.3
  npm install --no-audit --no-fund      # NO package argument — regenerates lock only
'

# 2) PROVE the lock is cross-platform-correct BEFORE committing (same checks CI runs).
grep -q "\"node_modules/@biomejs/cli-linux-x64\"" package-lock.json \
  && echo "OK: linux biome binary present" \
  || { echo "FAIL: linux biome binary MISSING — do not commit"; exit 1; }
grep -q "@rolldown/binding" package-lock.json \
  && { echo "FAIL: rolldown present (vite 8 crept back) — do not commit"; exit 1; } \
  || echo "OK: no rolldown (vite 5.4 as pinned)"
grep -m1 '"version": "5.4' <(grep -A2 '"node_modules/vite"' package-lock.json) \
  && echo "OK: vite pinned to 5.4.x"

# 3) Prove `npm ci` + the full gate the way CI will — again on linux, pinned npm.
docker run --rm -v "$PWD":/w -w /w node:26-bookworm-slim bash -euo pipefail -c '
  npm i -g npm@12.0.1
  npm ci --no-audit --no-fund           # the real lockfile gate — must succeed
  ./verify.sh                           # lint + typecheck + test + coverage + anti-tamper
'
# (verify.sh must stay executable = 100755. If the bit was lost: chmod +x verify.sh)

# 4) Commit the restored manifests + the regenerated lock TOGETHER, as one unit.
#    NEVER commit manifests without the matching lock, or a "lockfile sync" that
#    shows any manifest diff (that is not a sync).
git add package.json apps/api/package.json apps/web/package.json package-lock.json
git commit -m "fix(ci): pin npm@12.0.1 + Node26 upgrade (ADR-0005); regenerate lockfile on linux; restore vite5.4/vitest2.1 pins; lockfile cross-platform guard"
git push
```

Then CI runs `verify.sh` (linux, pinned npm) + `migrations` + `integration` + `sca`
+ the new `lockfile-guard` → `all-green` is the binding signal.

**If you cannot run Docker (no local linux at all): use the CI regeneration job
below — this is the recommended no-Docker path.**

## NO-LOCAL-LINUX path (recommended) — regenerate the lock via GitHub Actions

A dedicated manually-triggered workflow (`.github/workflows/regen-lockfile.yml`)
regenerates the lock **on ubuntu** with the pinned npm, proves it is
cross-platform-correct, and uploads it as a **downloadable artifact**. You download
it and commit it — no Docker, no local linux. Default is artifact-only
(`permissions: contents: read`, no push token) — safe, no branch-protection concerns.

**Exact click-path + commands:**

```bash
# A) Commit the RESTORED manifests first (devops already fixed the files in the
#    working tree). The lock is intentionally NOT committed here — the CI job makes it.
git rev-parse --abbrev-ref HEAD        # -> feature/s0-s1-foundation-auth
git status --short                     # expect the 3 package.json modified
rm -f package-lock.json                # discard the stale darwin/vite8 lock
git add package.json apps/api/package.json apps/web/package.json .nvmrc .github/workflows/ci.yml .github/workflows/regen-lockfile.yml docs/adr/0005-runtime-baseline-node26-npm12.md workspace/ci-toolchain-fix.md
git rm --cached package-lock.json 2>/dev/null || true
git commit -m "refactor(toolchain): upgrade to Node 26 / npm 12.0.1 (ADR-0005)"
git push
#    (CI will be RED on this intermediate commit — no lock yet. Expected; you are not
#     merging. The regen job below produces the lock.)
```

```
# B) Trigger the linux regeneration job (browser — GitHub Actions tab):
#    1. Repo → Actions → workflow "regen-lockfile" (left sidebar).
#    2. "Run workflow" → Branch/ref: feature/s0-s1-foundation-auth → Run workflow.
#    3. Wait for the green run. It regenerates the lock on ubuntu with npm@12.0.1,
#       asserts @biomejs/cli-linux-x64 is present + no @rolldown/binding, and runs
#       `npm ci` to prove the lock. If it fails there, a manifest still pulls vite 8
#       — fix the manifest, push, re-run.
#    4. Open the finished run → "Artifacts" → download "package-lock-linux"
#       (a zip containing package-lock.json).
```

```bash
# C) Drop the downloaded lock in at the repo root and commit it WITH nothing else:
unzip -o ~/Downloads/package-lock-linux.zip -d .    # -> ./package-lock.json
# Prove locally before committing (no linux needed — just reads the file):
grep -q '"node_modules/@biomejs/cli-linux-x64"' package-lock.json && echo "OK linux biome"
grep -q '@rolldown/binding' package-lock.json && echo "FAIL rolldown" || echo "OK no rolldown"
git add package-lock.json
git commit -m "fix(ci): add linux-generated package-lock.json (regen-lockfile job)"
git push
```

Your push in step C re-triggers CI → `verify`/`migrations`/`integration`/`sca` +
`lockfile-guard` → `all-green`. Because *you* pushed (not the bot), CI runs normally.

**Optional commit-back variant (advanced):** the regen job can push the lock straight
back to the branch instead of uploading an artifact — set the job `permissions:
contents: write` and add a commit+push step (`git config user...`; `git commit
package-lock.json`; `git push`). Caveat: a push made by `GITHUB_TOKEN` does **not**
re-trigger workflows (loop-prevention), so CI won't auto-run on the bot's commit —
you'd push a trivial follow-up commit to kick CI. The artifact path (default) avoids
this and keeps least privilege, so it is recommended.

### Why not `npm install --os=linux --cpu=x64` on macOS?
**Not reliable for the lockfile — do not use it as the fix.** `--os`/`--cpu` override
the platform npm uses to pick which optional deps to place in **`node_modules`**;
they change the install *target*, not the lockfile-completeness behavior that is
bug #4828. In practice they flip *which* platform's entries land in the lock (you can
get the linux entries but drop the darwin ones), and their effect on the lock's
`packages` map vs just `node_modules` is not guaranteed across npm versions. The
committed lock must serve **all** platforms (linux CI + macOS dev), so generate it on
a real linux environment (the CI job above). `lockfile-guard` is the backstop either way.

The Docker `node:26` sequence from the section above works too; use whichever is

## Prevention (so it cannot recur)

- **Never `npm install <pkg>` casually** on this repo — it rewrites `package.json`
  in place (this is how `nvm@0.0.4`, vite 8, and vitest 4 kept coming back). Add a
  dep by hand-editing the manifest, then `npm install` (no arg) to regen only the lock.
- **A lock-sync commit must show ZERO manifest diff.** `git diff --cached
  package.json apps/*/package.json` before committing any "sync lockfile" commit.
- **Regenerate the lock on linux**, always (docker step above). Local macOS `verify`
  passing is NOT evidence CI (linux) is green when native optional deps are in play.
- **`lockfile-guard` is the backstop** — it will block a darwin-only or vite-8 lock
  at the PR gate no matter what.

## Infra-cost & security notes

- **Cost:** none. All changes are CI/toolchain — no new AWS resources. Marginally
  more CI minutes (one `npm i -g` per job + a tiny guard job, seconds each);
  negligible against the $365/mo runtime budget.
- **Security:** `npm i -g npm@12.0.1` pins the resolver → **reduces** supply-chain
  variance (deterministic dependency resolution feeds the existing `sca`/gitleaks
  gates). No secrets touched. `lockfile-guard` only reads the committed lock. Pinning
  npm exactly is a supply-chain hardening win, consistent with the SBOM/SCA posture.
